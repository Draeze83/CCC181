## Did my persona rules hold up?

### Aira Villanueva (person waiting)

| Rule | Held up? | Evidence from the test |
| --- | --- | --- |
| Because students may not know which office service matches their need, my interface must show plain-language service names and instructions before ticket creation. | Yes | Luigi was able to clearly understand every text in the web app |
| Because students currently wait without knowing when their turn will come, my interface must make the ticket code, current status, and number of people ahead easy to find. | Yes | He was able to easily lookup his position in the queue |
| Because waiting can conflict with classes and deadlines, my interface must refresh ticket status automatically, show when it was last updated, and label any wait-time figure as an estimate. | Yes | These details have already been implemented |

### Ramon Dela Cruz (staff member)

| Rule | Held up? | Evidence from the test |
| --- | --- | --- |
| Because the project covers multiple service types, my interface must keep the active service and counter unmistakably visible before staff call a ticket. | Yes  | There is a table that shows the details of the customer ticket including the service they availed |
| Because staff need to move tickets through a consistent workflow, my interface must make the next valid action easy to identify and prevent invalid status changes. | Yes | There are clear action buttons in the staff dashboard |
| Because students' identities and private records should not be exposed on a public queue board, my interface must use ticket codes for public display and keep staff-only controls behind authentication. | Yes | The customer ticket does not show their name in their ticket, only in the staff dashboard |
